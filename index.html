Problem

知識管理的五大困境

資訊碎片化
散落各處，難以整合
知識遺忘
讀過即忘，重複搜索
缺乏連結
脈絡缺失，孤立文件
重複勞動
每次重新解釋背景
無法累積
知識停在「點」層次
核心問題：你的知識不會自動幫你「工作」。讀了、存了、卻還是沒辦法複用。
Traditional Solution

RAG 的限制

✗ 無真實理解
只有查找，沒有整理過的知識
✗ 碎片仍是碎片
取出來的內容依然缺乏結構
✗ 更新成本高
加入新資料需重新 embedding
✗ 難以追溯
AI 說了什麼、從哪來，不透明
RAG 解決了「找得到」的問題，但沒有解決「知識沒有被真正組織」的問題。
Core Concept

LLM Wiki

一句話核心：讓 LLM 扮演維基編輯，每次輸入新資料，智慧地更新相關詞條，而不是另起爐灶。
Comparison

RAG vs. LLM Wiki

RAG
✗知識組織：碎片化向量，無結構
✗查詢方式：每次從原始資料檢索
✗知識更新：重新 embedding，成本高
✗可解釋性：來源難以追溯
✗知識積累：不累積，每次重頭
VS
LLM Wiki
✓知識組織：結構化 Markdown，有頁面連結
✓查詢方式：LLM 直接讀整理好的 wiki
✓知識更新：增量 update，保留歷史
✓可解釋性：清楚可讀，人可直接審閱
✓知識積累：複利增長，越用越強
How It Works

運作流程

① Schema
撰寫 schema.md，定義主題分類與頁面格式
② 原始資料
任何格式：PDF、Markdown、對話紀錄
③ LLM 整合
智慧更新既有頁面，或新增頁面
④ 連結
Wikipedia 式相互連結，形成知識網絡
⑤ 查詢
LLM 讀已整理的 wiki，品質更高
Schema

Schema 的角色

schema.md 
# Wiki Schema: AI Research KB

## Structure
- concepts/   # Core ML/AI concepts
- papers/     # Paper summaries
- people/     # Researchers
- tools/      # Libraries & techniques

## Page Format
title: <topic>
related: [[concept-a]], [[paper-b]]
summary: <2-3 sentence overview>
details: <notes, examples>
關鍵：Schema 是「憲法」——定義知識庫骨架，讓每次更新都朝同一方向累積，不散亂增生。
Use Cases

應用場景

個人知識庫

研究人員把每天讀的論文自動整理進個人 wiki，下次研究相關主題有完整脈絡。

企業知識管理

會議紀錄、設計文件增量整合進企業 wiki，新員工 onboarding 有豐富組織知識支撐。

學術研究追蹤

自動追蹤特定領域最新論文，維護「研究現況 wiki」，隨時告知最前沿進展。

AI Agent 記憶層

作為 Agent 的長期記憶後端，每次行動後更新 wiki，下次執行有連貫上下文。

Karpathy 本人的用法：用 LLM Wiki 管理自己的技術知識，涵蓋 ML 論文摘要、工具評比、程式設計心得。

複利知識 增量更新 Schema-first Human-readable LLM as Editor 開放延伸
→ 「Compounding knowledge」：知識應像複利一樣滾動，不是線性堆疊
→ 增量更新（incremental update）：每次只改動有變化的部分，保留過去積累
→ Schema-first 設計：先定義結構，再餵資料，確保知識有序生長
→ Human-readable 優先：純 Markdown，人可直接讀、直接編輯
→ LLM as editor：LLM 扮演維基編輯，智慧決定更新哪裡、如何整合
這個 Gist 本身就是一份「LLM Wiki 的 Wiki」——用清晰的 Markdown 結構示範了他所提倡的方式。
